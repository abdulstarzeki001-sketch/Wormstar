# Wormstar Platform — Engineering Foundation v1

> أسس النظام الذي يجمع Wormstar AI Lab وSentinel وStatic iSH Audit.
> هذا الملف يميز بين **الوحدات المنفذة** و**التحسينات المستقبلية المقترحة**.

## الوضع الحالي — مُنفّذ

| النظام | المسؤولية | موقع المصدر |
| --- | --- | --- |
| Core Worker | مصادقة المالك، سياسات التشغيل، نماذج AI، D1/Vectorize، وكلاء مهام محددة | `cloudflare-worker/` |
| Sentinel Worker | الواجهة العربية والإنجليزية، اختيار النموذج والمهمة وعمق التفكير، وكيل API مصادق عليه | `wormstar-ui/` |
| iSH Static Audit | فحص ساكن دون تنفيذ الكود، محلي على iPhone/Linux، وعرض تقارير JSON المنقحة | `integrations/star-cyber-audit-ish/`, `wormstar-ui/audit-worker.js` |
| Quality Gate | اختبارات الأربع وحدات، كشف الأنماط الخطرة المضافة، التحقق من JSON | `.github/workflows/quality-gate.yml` |

## قواعد معمارية غير قابلة للمساومة

1. **الصلاحيات في الخادم فقط:** لا تُرسل أسرار AI أو D1 أو Cloudflare إلى الواجهة أو تقارير السجل. لا تقبل طلبًا من عميل غير مصادق على نقاط Core الخاصة.
2. **Service Boundaries:** تتواصل Sentinel مع Core بواسطة `CORE` Service Binding. مختبر iSH الساكن يُخدم كملف محلي ولا يرث صلاحيات Core ولا يرفع ملفات المستخدم تلقائيًا.
3. **عزل البيانات:** D1 يخزن نصوص المراجع، Vectorize يخزن المتجهات ومعرّفاتها، وملفات التدريب المحلية لا تُرفع من دون موافقة.
4. **تنفيذ مصرح به:** الوكلاء الحاليون يقترحون وينجزون تحليلات نصية محددة. أي تشغيل خارجي على أجهزة/مواقع يحتاج تحديد مالك ونطاق وموافقة وسجل قابل للمراجعة. التشغيل على أجهزة غير مصرح بها غير مقبول.
5. **المخرجات موثّقة:** لا تُصنف نتائج تحليل ثابت أو غياب Header بأنها اختراق مؤكد. أعرض `modelUsed` و`fallbackUsed` ومراجع RAG والتباس النتائج.
6. **المسؤوليات مستقلة:** واجهة UI لا تدمج بيانات الاعتماد أو منطق سياسات Core، والاختبارات لا تعتمد على ملفات خاصة أو مفاتيح فعلية.

## عقد AI الحالي

- `POST /api/auth`: Bearer owner token، ولا يحتفظ به عميل Sentinel بشكل دائم.
- `POST /api/chat`: `mode`, `message`, `history`, `engine`, `reasoningEffort` و`memoryIds` في جسم JSON بعد المصادقة.
- `engine=auto` يختار حسب المهمة؛ يستطيع المالك اختيار 120B و20B وQwen Coder.
- `reasoningEffort`: `auto | low | medium | high`. عند تعارض `high` مع ميزانية إخراج صغيرة يهبط المستوى إلى `medium` لتجنب استنفاد الرموز في الاستدلال دون إجابة.
- يختلف تنسيق ردود Workers AI حسب النموذج؛ `model-runtime.js` يوحّد نص الإجابة دون عرض حقول الاستدلال الداخلي.
- **الحدود الفيزيائية موجودة:** ذاكرة ووقت تشغيل Cloudflare، نافذة سياق النموذج، ميزانية الرموز، وسياسة المالك. الحد الأعلى المسموح في سياسة Core لرموز الإجابة 4096، وقد تكون القيمة المحفوظة فعليًا أقل إلى أن يعدّلها المالك. لا توجد نماذج ذات سعة لا نهائية.

## Quality Gate — قاعدة النشر

يعمل قبل كل نشر Cloudflare:

- `npm test` في Core: سياسات، مصادقة، RAG، نموذج AI، واختبارات أمنية.
- `npm test` في Sentinel: بناء، syntax، المسارات، ووكيل API، وربط iSH المحلي.
- اختبارات Python على لقطات تركيبية، ثم `analyze.py --local wormstar-ui` دون اتصال بمواقع خارجية.
- `security-gate.mjs` يفحص الأسطر الجديدة بين SHA للـcommit وقاعدة التغيير، ويسجل النتائج بـSHA، ويمنع إضافة أنماط خطرة عالية/متوسطة. التغييرات في كود الاختبار واللقطات المرجعية مستثناة من هذا الماسح، لكنها تخضع لاختباراتها.
- يتم حفظ Artifacts منقحة؛ تنبيهات المحلّل الساكن ذات دلالة **مراجعة هندسية** وليست درجات CVSS أو ثغرات مؤكدة.
- وظيفة Deploy `needs: quality` فلا تبدأ إذا فشلت أي وظيفة جودة. لا تحصل وظائف الاختبار على أسرار Cloudflare.
- بعد النشر: فحص Core عبر Integration Hub لأن Core العام قد يحتاج تسجيل دخول، وفحص Sentinel وiSH عبر واجهات الحالة. هذه فحوصات صحة وليست إثباتًا لاكتمال سيناريوهات الذكاء المصادق عليها.

## سير عمل تطوير أي وحدة جديدة

1. حدّد الواجهة ومخطط البيانات ونقاط الصلاحية والحدود التقنية.
2. أضف وحدة مستقلة واختبارًا لها، ولا تعدّل Core الضخم إلا في نقطة ربط واضحة.
3. أضف اختبارات نجاح وفشل وهوية خاطئة وحجم بيانات غير صالح.
4. حدّث الواجهة والوثائق والنسخة التجريبية، ثم افتح Pull Request.
5. اطلب مرور بوابة الجودة؛ افحص مخرجات التقرير وما تغيّر في API.
6. انشر نسخة منضبطة، ثم تأكد من الصحة والواجهات الأساسية. عند وجود خطأ، عُد إلى نشر سابق سليم.

## خطة توسعة مستقبلية — **غير منفّذة بعد**

**P1 — قابلية الصيانة:** تقسيم `cloudflare-worker/worker.js` الكبير تدريجيًا إلى routers مستقلة (identity, chat, retrieval, agents, audit)، ونسخ API منظمة. إضافة tracing آمن وإدارة أخطاء مشتركة.

**P2 — وظائف طويلة المدة:** استخدام Queues + Workflows للمهام المصرح بها طويلة الأمد، وDurable Objects للجلسات التفاعلية حيث يلزم تزامن حقيقي. R2 للمرفقات الكبيرة بدل حشر الملفات في D1.

**P3 — جودة AI:** مجموعة تقييم عربية/إنجليزية واقعية ومجهّلة، قياس faithfulness ونسبة الاسترجاع والكمون والتكلفة، وتقييم دوري للنماذج (120B/20B/Qwen) دون افتراض تفوق نموذج من الاسم وحده.

**P4 — توسع الفريق:** فصل حسابات المستخدمين عن رمز المالك المشترك، أدوار وصلاحيات لكل فريق، مراجعة تغييرات البنية وقواعد البيانات، نسخ احتياطية واسترجاع اختباري وبيئة Staging منفصلة.

**P5 — الأوزان المستضافة:** تدريب LoRA على GPU خارجي واختبار جودته قبل التفعيل، مع بقاء Core مخوّلًا لطبقة الوصول. لا تدّعي المنصة أن تدريب LoRA يتم داخل Workers.

## مخاطر متبقية

- لا تزال واجهات إحصائية تجريبية موجودة؛ يجب وسمها بوضوح حتى توصل بحقائق مدعومة.
- JWT/OIDC متعدد المستخدمين، وسياسات الأدوار، ودورة الحياة المعقدة للوكلاء لم تُنفذ بعد.
- التقييم الواقعي لنوعية ردود AI بحاجة إلى اختبارات مالك مصادق عليها وبيانات تقييم خالية من الأسرار.
- إعدادات Cloudflare وخطط الموارد تحكم السعات والكمون والتكلفة، حتى مع قابلية توسعة التصميم.
